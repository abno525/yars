# M4 Chat per finding Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every finding has a chat beside it: threaded messages that can be anchored to a section and resolved, workflow events in the same timeline, open-thread counts in the findings table, live refresh by polling.

**Architecture:** `internal/chat` parses/serialises the append-only `chat.jsonl` and folds messages into threads. `store` appends messages (one commit each, authored by the poster) and, for workflow transitions, writes the event message in the same commit as the status change. `index` counts open threads per finding. `web` shows a chat column next to the finding (stacked on narrow screens), with per-section "Comment" links and counters, polling every 5 s.

**Tech Stack:** Go 1.27, encoding/json, net/http, html/template, htmx 2.0.4.

**Spec:** `docs/superpowers/specs/2026-11-03-yars-design.md` (section "Chat").

## Global Constraints
- File: `engagements/<eng>/findings/<dir>/chat.jsonl`, one JSON object per line, append-only (existing lines are never rewritten).
- Message JSON: `{"id","ts","user","text","section"?,"reply"?,"resolves"?,"reopens"?,"event"?}`; `ts` RFC 3339 UTC; `id` = 12 lowercase hex chars (random).
- A thread is a message with no `reply`; replies point at the thread id. A thread is resolved when the latest `resolves`/`reopens` message for it is `resolves`.
- Event messages (`event` = action name, e.g. `submit`, `return`) are written by workflow transitions; `return` carries the reason as `text`. Events are not threads and can't be replied to or resolved.
- `.gitattributes` at the data-repo root contains `chat.jsonl merge=union` (store ensures it, committed with the first chat message if missing).
- Commit subjects: `F-001: comment` (new thread), `F-001: reply`, `F-001: resolve thread`, `F-001: reopen thread`; workflow commits keep their M3 subjects.
- Text limits: 1–10 000 chars after trimming; Markdown rendered with the same goldmark config as sections (raw HTML off).
- Anyone logged in may post, reply, resolve and reopen, in every status (chat stays open after approval).
- Polling: the message list re-fetches every 5 s via `hx-trigger="every 5s"` and only swaps when the content hash changed (server returns 204 when the client's `since` hash is current).
- Shell usage: Write/Edit for files; single plain commands, no pipes/heredocs/`cd`/chains.

## Review Focus
1. A corrupt or hand-edited line in chat.jsonl (bad JSON, unknown thread id): skipped, the rest of the chat still shows (Task 1 `TestParseSkipsBadLines`).
2. Reply/resolve pointing at a missing or event message id: rejected with 400, nothing written (Task 2 `TestPostChatRejectsBadRefs`).
3. A message containing `<script>` or raw HTML: escaped in the page (Task 4 `TestChatEscapes`).
4. Two messages posted at the same time: both lines kept, file stays valid JSONL (Task 2 `TestPostChatConcurrent`).
5. Polling with no changes must not swap (no flicker, no lost draft in the textarea) (Task 4 `TestChatPoll204`).

### Task 1: `internal/chat`

**Files:** Create `internal/chat/chat.go`, `internal/chat/chat_test.go`.

**Interfaces — Produces:**
- `type Message struct{ ID, User, Text, Section, Reply, Resolves, Reopens, Event string; TS time.Time }` with the JSON tags above (omitempty on optional fields).
- `func Parse(b []byte) []Message` — skips blank/invalid lines.
- `func Line(m Message) ([]byte, error)` — one JSON object + `\n`.
- `func NewID() string`.
- `type Thread struct{ Root Message; Replies []Message; Resolved bool; ResolvedBy string }`.
- `type Item struct{ Event *Message; Thread *Thread }` and `func Timeline(msgs []Message) []Item` — events and threads in order of their first message; replies/resolves referencing unknown ids are ignored.
- `func OpenCount(msgs []Message) (total int, bySection map[string]int)`.
- `func Validate(msgs []Message, m Message) error` — text length; reply/resolves/reopens must reference an existing thread root (not an event, not a reply); at most one of reply/resolves/reopens.
