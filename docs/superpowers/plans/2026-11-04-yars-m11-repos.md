# M11 — one git repo per engagement, main repo with submodules

**Goal:** every engagement is its own git repository, so its history can be followed and cloned alone. The main repo holds `.yars/` and all engagements as submodules, so `git clone --recurse-submodules` downloads everything.

**Design:** `/home/plato/.claude/plans/the-goal-of-this-foamy-sunrise.md` (approved 2026-11-04), Milestone 11 section.

## Layout
```
<data>/                     main repo: .yars/, .gitmodules, engagements/<id> as gitlinks
  .yars/yars.db             (ignored)
  engagements/<id>/         a git repo of its own: engagement.yaml, findings/<dir>/…
```
- `.gitmodules` entry: `path = engagements/<id>`, `url = ../e/<id>`, `branch = main`.
- URLs:
  - main repo: `/git/yars`
  - one engagement: `/git/e/<id>`
- The server's data directory has the same shape as a recursive clone. The store therefore reads files from the same paths as before; only commits go to the engagement's own repo.

## Rulings
- **One store mutex, kept.** The design suggested one lock per engagement, but the team is 6 people and a single lock keeps the code simple. Cost if wrong: edits in different engagements wait on each other for a few milliseconds.
- **Gitlink commits use `git add <nested repo>`** (with `advice.addEmbeddedRepo=false`), not `update-index --cacheinfo`. It does the same thing and reuses `gitrepo.Commit`.
- **Engagement repos get their git-server settings lazily** on their first request, plus at startup. This also covers repos created by migration.
- **Main-repo pointers sync before every fetch of `/git/yars`** (one commit by `yars`, only if something moved) and when an engagement is created.

## Tasks
1. **gitrepo:**
   - `run` passes `-c advice.addEmbeddedRepo=false`;
   - `Commit` of a nested-repo path records a gitlink.

   Test: commit an embedded repo dir and check that `ls-tree` shows mode 160000.
2. **Store, multi-repo:**
   - `EngRepo(id)`;
   - commits are routed to the engagement repo with repo-relative paths;
   - `unmoved` checks the engagement HEAD;
   - `CreateEngagement`/`CreateRetest` init the nested repo, commit inside it, then add the `.gitmodules` entry and gitlink in main;
   - `SyncPointers()`;
   - `Version()` (all HEADs) for the index.

   Tests:
   - the engagement repo has the finding commits and main has none;
   - a gitlink and `.gitmodules` entry exist after create;
   - `SyncPointers` makes one commit, then none.
3. **Index:** the key is `store.Version()` + database seq.
4. **Policy:**
   - `Checker.Eng` (engagement repo) vs main.
   - **Main:** only `.yars/**` (director, not server files), `.gitignore`, `README.md`, `.gitattributes`. Gitlinks, `.gitmodules` and `engagements/**` are rejected ("push to /git/e/<id>").
   - **Engagement:** `engagement.yaml` is director only; `findings/<dir>/finding.md` and `findings/<dir>/attachments/**` as before; everything else is rejected.
5. **gitserve:**
   - routes `/git/yars` and `/git/e/<id>` (the engagement must be a repo; otherwise 404);
   - per-repo hardening and hook;
   - `SyncPointers` before upload-pack on `/git/yars`.
6. **Hook:** `yars hook pre-receive` maps `GIT_DIR` to main or an engagement.
7. **Web:** the engagements page shows the clone-everything command; an engagement page shows its own clone URL.
8. **Migration** (`yars migrate`, second step):
   1. `git subtree split -P engagements/<id>`;
   2. `git rm -r --cached`;
   3. `git init` in place and fetch/reset to the split commit;
   4. `.gitmodules` entry and gitlink, one main commit.

   If subtree fails, fall back to one import commit. `legacyItems` reports engagements that are not repos yet.
9. **End to end (`cmd/yars/push_test.go`):**
   - a recursive clone over HTTP gets every engagement;
   - a push in a submodule (on its `main` branch) lands;
   - `git clone /git/e/acme` history has only acme commits.
10. **Docs:** `docs/mcp.md` gets the clone commands (`git switch main` inside an engagement before committing).

## Review focus
- A push to the main repo after the server bumped pointers (non-fast-forward: the director must pull first).
- `updateInstead` on the main repo with nested repos that moved ahead (submodule changes must not count as a dirty tree).
- A path-traversal engagement id in `/git/e/<id>` (must pass `ValidID` and be an existing nested repo).
- An engagement deleted from disk while the main gitlink still exists.
- Cloning over HTTP with relative submodule URLs and credentials in the URL.
