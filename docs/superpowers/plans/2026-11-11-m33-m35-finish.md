> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Read `RUN.md` and `2026-11-11-yars-roadmap-to-v1.md` first. Steps use checkbox (`- [ ]`) syntax.

**Goal:** the three things left once every feature is in: a stylesheet in which every colour is a token (so the later dark-mode remake only changes values), a backlog with nothing undecided in it, and a release candidate that has been walked through end to end.

**Spec:** `docs/open-decisions-2026-11-07.md` D6 and R9 (dark mode is remade later, by the user, on the canvas; the toggle stays), `docs/superpowers/deferred-minors.md`, the Verification section of `docs/superpowers/specs/2026-11-03-yars-design.md`.

**Not in these milestones:** new dark colours. The dark theme keeps the values it has; choosing new ones is a design task for the user after v1.0.

3. A backlog line closed as "fixed" without a test that would catch it coming back (M34 rule 1).

## M33 — every colour is a token

**Branch:** `pr/27-colour-tokens` from `pr/26-mcp-v2`.

### Task 1: no colour literal outside the token blocks

**Files:** modify `internal/web/static/style.css`; create `internal/web/theme_test.go`

Rule: outside the three token blocks (`:root { … }`, `@media (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { … } }`, `:root[data-theme="dark"] { … }`) the stylesheet contains no colour literal: no `#` followed by 3, 4, 6 or 8 hex digits, no `rgb(`, `rgba(`, `hsl(`, and no colour keyword except `transparent`, `currentColor` and `inherit`. A literal found today becomes a new token named for its use (`--chat-event-line`, not `--grey-3`). Its light value is the literal. Its dark value is: the literal that the same rule has inside a dark-only selector today, if there is one; otherwise the dark value of the existing token whose light value is equal to the literal; otherwise the same literal (listed in the PR body as "needs a dark value"). *(Built: the second source was not used. It would have changed the dark theme, which step 5 forbids: white text on tags would take `--bg`'s black. Every new token keeps its literal in both themes; see `review-after.md`, M33 task 1.)*

- [x] **Step 2:** run them. Expected: FAIL with a list. **Step 3:** replace each literal with a token. **Step 4:** run `go test ./internal/web`. Expected: PASS, the pixel tests included.
- [x] **Step 5: browser check** in light and in dark: screenshots, before and after, of the pages listed in step 5 of task 2 in `2026-11-11-m22-hardening.md`; no page changed in either theme. Commit: `refactor(css): every colour is a token`.

## M34 — polish backlog

**Branch:** `pr/28-polish` from `pr/27-colour-tokens`.

### Task 1: triage `docs/superpowers/deferred-minors.md`

Every line gets one of four marks, written into the file as a prefix: `[fixed <commit>]`, `[do]`, `[won't: <reason>]`, `[ask]`.

Rules:
1. `fixed` needs a test that fails without the fix. Find the fixing commit with `git log --oneline -S<keyword> -- <file>`. If there is no such test, write it first: if it passes, the line is fixed (the test stays); if it fails, the line is `do`.
2. `do`: the fix is under about 50 changed lines and changes no behaviour a decision in `docs/open-decisions-2026-11-07.md` fixed.
3. `won't`: the line is about something that no longer exists (for example `chat.jsonl`), or is a test gap for code that was removed.
4. `ask`: everything else. These are not built. They go to `docs/known-limits.md` under the heading "Needs a decision", each with a one-line recommendation.
