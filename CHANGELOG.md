# Changelog

What changed for people who run or use YARS. Newest first.

## Unreleased

### Added

- The Inbox updates itself: a finding sent for review, a sign-off, a reply, a notice or a new lead on a team board shows within about two seconds, with no reload. The Inbox badge of the top bar follows on every page that updates live (a finding, the findings list, the team board, the Inbox). A refresh waits while rows are ticked, a menu or the reason panel is open, a bulk run's result is shown or more rows were loaded.
- Sign off and Approve on the finding page open the next finding of the queue: Awaiting my review after a Sign off, Ready to approve after an Approve, in the Inbox's order (before: the same finding again). With none left the page stays on the finding.
- A page opened without a session comes back after the login (before: always the start page). A form sent after the session expired comes back to the page it was on. The address is a path of this site only.
- The Return, Withdraw and Revert reasons of the finding page are sent without leaving the page: with an expired session the reason stays in its box under a Session expired toast (before: the login page, and the reason was lost).
- An error answered to a page request is a page in the layout, with the top bar: the status, the reason, and on a server error the request's ID (before: bare text). htmx requests, scripts and downloads get the plain text as before. A missing engagement and one the account is not on are the same page.
- The page of a finding that was merged into another opens that finding. The merged one is still opened from the link in the target's chat (`merged in: F-001`) or with `?source=1` on its address; its history and its Restore are unchanged.
- Every editor keeps what is typed as a draft in the browser: a section, CVSS, Details, Affected assets, a team board reply and a new lead (before: a section only, and only when the session had expired). An editor opened again offers it with Restore. The draft is finding text stored in the browser's profile (`localStorage`), per account, for up to 14 days; it is never sent anywhere, and it goes on Save, Cancel, a confirmed Discard and Log out.
- Settings › About shows the version, the license and a link to the source.
- The licence texts of the vendored fonts and htmx ship with the binary; `NOTICE` lists all third-party work.
- `SECURITY.md`, `CONTRIBUTING.md` and issue templates.
- `log.level` (`debug`, `info`, `warn`, `error`) and `log.format` (`text`, `json`) in `.yars/config.yaml`, and `yars serve --log-level`, set what the service log holds and how it is written ([docs/config.md](docs/config.md)). Both keys are read at the start.
- The service log has one line for each request to the website, the git endpoint and MCP: an ID, the method, the route, the status, the time taken, the account, the token's ID, the engagement and the finding. A request over 2 s is a warning. Static files are logged at `debug`. A handler's panic is one line with the whole stack trace in `stack`.
- The service log holds IDs and usernames, never text: an attribute named like a password, a token's value, a key, a cookie, a title, a reason or other text is dropped, and an error's text loses a finding's folder name (its ID stays), an attachment's name, and the login and query of an address. The error of a failed git command leaves out the commit message.
- Every response carries its request's ID as `X-Request-ID`. An internal error shows it on the page and in the toast (`Request 4f2a9c1b`), and the error's log line has the same ID.
- The background work writes a line when it ends, with the time taken and the outcome: a check run, an AI call, an export, a webhook delivery, a mail, a push (accepted or refused), a backup download, a restore upload and the daily prune. A webhook delivery that is tried again, a failed AI call, a mail that is not sent and a wait of over 5 seconds for a repository's lock are warnings. The start line names the version, the schema, the workflow, the address and whether AI, SMTP and pandoc are on.
- An AI call the provider refused is one `warn` line, `ai call failed`, with `status` and `host`. The line `ai: the provider refused a call` is gone.
- A webhook delivery that got no HTTP answer says why in `err`, in one fixed word (`no answer`, `redirect refused`, `secret`, `address`, `removed`, `disabled`, `database`). A delivery dropped because its webhook was turned off is an `info` line, `webhook delivery dropped`.
- `yars status --data <dir>` prints what the running server does now: the checks running and queued, the waiting webhook deliveries, the open event streams, the repository locks and the last 200 warnings and errors. It reads the server over a socket in the data folder (`.yars/status.sock`), needs no password, and runs as the service account.
- Admin › System has two new panels. Current state shows the same as `yars status`. Log shows the last 200 warnings and errors of the service log; they are kept in memory and lost at a restart.
- Admin › System › Log has the switch Debug level for 15 minutes: it sets the service log to `debug` without a restart and turns itself off. Each change is in Admin › Activity.
- The finding page has a Take back button, beside Withdraw, for the author and a director while the finding is in verification (before: the bulk bar and MCP only). Its key is Shift+T, and it acts at once, as every workflow key.
- Over MCP, `tools/list` gives each tool its annotations: `readOnlyHint`, `destructiveHint` and `openWorldHint` ([docs/mcp.md](docs/mcp.md)).
- Admin › Webhooks: the Deliveries panel of a webhook has New secret and Send test. New secret replaces the secret in place and shows it once; the deliveries stay (before: delete the webhook and add it again, which removed them). Send test sends one signed delivery of the event `ping`, listed with its status. Both are in Admin › Activity (`webhook.rotate`, `webhook.test`).
- More notifications, each with a row in Settings › Notifications: New thread (a new thread on your finding), Signed off (a reviewer signed off your finding), Withdrawn and Reported (a finding you wrote or review), Unassigned (you were taken off the reviewers of a finding in verification) and Retest assigned (a retest was made for you). A restore of a withdrawn finding is Reverted. A reviewer whose sign-off an edit, an attachment or a push voided gets Review requested again, with the text `sign-off voided`. `@name` in a message on the team board is Mentioned, and its notice opens the lead. An account that saved its notification choices before gets the new ones in app. Over MCP, `list_notifications` gives a lead's ID as `ref`. The database schema is 30.
- `GET /healthz` answers a probe without a login: `200` and `ok` when the server answers and its database reads, `503` and `unavailable` when not. It holds no version, no counts and no reason; the reason is one `warn` line of the service log, `health check failed`, when the answer turns bad. A probe answered `200` is logged at `debug` ([docs/deploy.md](docs/deploy.md)).
- `yars help`, `yars -h` and `yars --help` print the list of commands and exit 0, and `yars --version` prints what `yars version` prints (before: all four printed the list as an error and exited 2). `yars <command> -h` lists the command's flags and exits 0 (before: `yars: flag: help requested` and exit 1 or 2). A word that is no command is named: `yars: unknown command "x"`, then the list, exit 2.
- `yars users --data <dir>` lists the accounts: name, role, admin, disabled, created. `yars disable <user>` and `yars enable <user>` do what the Disabled switch of Admin › Users does, also while the server runs: a disabled account cannot log in, its sessions end at once and its tokens are refused. Both are in Admin › Activity by `cli` ([docs/deploy.md](docs/deploy.md)).
- A backup is of one moment: it records the commit each repository was at when the database was copied, and a restore resets each repository to it (before: a change that landed while the backup was taken was in the files and not in the database). `yars restore` prints `point in time: yes` or `no`, and the Restore panel of Admin › System has a Point in time cell. A backup from an earlier YARS restores as before and says `no`. A backup taken while a Purge rewrites a history fails, and `yars backup` takes it again.
- Admin › System › Run integrity compares the database with the finding files, in the new Health row Database and files: it counts rows kept for a finding that is gone and approvals given for other text, and reports a finding ID held by two folders or a `finding.md` that does not read as an error.
- A pattern rule can leave out code: `exclude: code` in the rule file, or the Skip code box of the rule editor. The rule then does not match inside fenced blocks, indented blocks and code spans of a section. A `yars` on a pentester's machine from before this release reads such a rule as `rule invalid: unknown field(s) exclude`: update it once a rule uses the key ([docs/rules.md](docs/rules.md)).
- A dismissal covers the matches its result had when it was made: the same wording added to that place later opens the result again (before: it stayed dismissed for good). The Dismissed table shows the number in the column Covers · By. A dismissal from before shows — and gets its number at the next Check of the finding. The database schema is 31 ([docs/rules.md](docs/rules.md)).
- A Check gives each script and each AI rule 90 s for itself (before: 90 s for all of them together, so the rules after a slow AI rule timed out, and a script among them failed the Check and held Sign off and Approve). A Check with many slow rules now takes longer. `yars lint --all`, the pre-commit check, a git push, the Test bench and Submit keep 90 s for the whole run ([docs/rules.md](docs/rules.md)).
- A section or details row renamed on Admin › Structure is renamed in the rule targets too, in the same commit (before: a `not-empty` rule on the old name reported an empty part on every finding and blocked Submit). A finding's stored check results and their dismissals move to the new name. The rules changed with the rename, so every finding needs a new Check after it ([docs/rules.md](docs/rules.md)).
- The Inbox has a Check stale button with a count. After a rule changes, every checked finding waits for a new Check; the button starts those checks for the findings of your Awaiting my review and Ready to approve queues, in the simple workflow for the drafts you wrote, 100 at most per press (before: one click on Check per finding). Such a check notifies the author only when it leaves an open error ([docs/rules.md](docs/rules.md)).
- The rule editor on Admin › Rules has a Try unsaved button: it runs the editor's values on the finding the Test bench has selected and shows the hits there, before the rule is saved (before: the bench ran saved rules only). It writes nothing. A script rule runs its saved script ([docs/rules.md](docs/rules.md)).
- The Checks strip has a Cancel button while a Check or a Fix with AI runs on the finding, also while the Check waits in the queue (before: neither could be stopped). A cancelled Check leaves no results, no thread and no notification, and the Check before it counts again for Sign off and Approve. A cancelled fix keeps what it committed and is followed by no Check. Over MCP, `lint_finding all=true` answers the state `cancelled` for a run cancelled meanwhile ([docs/rules.md](docs/rules.md)).
- The check queue shares its places between accounts: a free place goes to the account whose checks hold the fewest, then to the one that waited longest (before: first in, first out for everybody, so one Check stale press of 100 checks kept every other account's check behind them). One account's checks keep their order ([docs/config.md](docs/config.md)).
- Admin › AI has a Limit beside the prices: the most the AI calls of the last 30 days may cost. Once it is reached, AI rules are skipped with the warning `AI rules skipped: the AI spend limit is reached`, a Check goes on without them and holds nothing, Fix with AI is refused with words, Admin › AI shows Limit reached and the service log has one `warn` line (before: usage was only recorded). A limit needs a price. The list of AI calls is now kept for at least 30 days, also with fewer Audit log days ([docs/rules.md](docs/rules.md)).
- Admin › Rules has a Rule pack panel. Add starter rules writes a small set of pattern and built-in rules that ships with YARS, each turned off (`yars init` still writes none). Export downloads every rule as one YAML file; Import adds the rules of such a file, each turned off, and skips an ID that exists. A pack is checked as the editor checks a rule and refused whole on one problem; it brings no scripts. Each of the two presses changes the rules, so every finding needs a new Check after it ([docs/rules.md](docs/rules.md)).
- An engagement's Settings tab has an AI switch for a client that allows no AI on its findings; a director flips it. Off, no AI rule runs on the engagement's findings on any path (a Check, `yars lint --all`, MCP, the Test bench), Fix with AI is refused with `AI is off for this engagement`, an answer kept from before is not used, and nothing of the findings is sent to the provider. The switch is the key `ai: off` in `engagement.yaml`, so a clone has it; any value but `on` and `off` is refused on the page and on a push, and so is the key in another letter case (`AI: off`). A retest takes its source's switch. The change is in Admin › Activity as `eng.ai` ([docs/rules.md](docs/rules.md)).
- A rule can be limited to engagements: the key `engagements` lists their IDs, and the rule runs, and is a step of a Check, only there. The key is written in the rule file; the rule editor and a rule pack keep it ([docs/rules.md](docs/rules.md)).
- A rule script's input has the finding's engagement: `engagement`, its ID. Every script rule runs once more at the next Check of each finding.
- Fix with AI also fixes a result on the title and on a details row (before: sections only, so a finding whose open results were all on its title answered `nothing to fix`). The commit is `edit title` or `edit details` by `AI for <user>`, under the checks a section's fix passes. A new title must be one line of at most 200 characters as the model wrote it: one with a line break is refused, never joined or cut ([docs/rules.md](docs/rules.md)).
- `docs/deploy.md` has a Logs section: the journalctl commands, the levels, the fields, what a line never holds, the request ID, and a fail2ban example for the failed-login lines in their new form.

### Changed

- The Go module is `github.com/abno525/yars`: `go install github.com/abno525/yars/cmd/yars@latest` builds the binary.
- Over MCP, `transition` with `clear`, `sign_off`, `approve` or `complete` needs `base`, the `hash` from `read_finding` (before: optional, so an agent could sign off a version it never read). Without it the call is refused with `invalid` and `missing argument "base": call read_finding and pass its hash as base, …`. An agent that signs off or approves must read the finding first and pass the hash. `read_finding` lists these actions with `needs: "base"`. The other actions are unchanged.
- Over MCP, text that people wrote moved under a key named `untrusted` in the object it belongs to, so an assistant can tell it from what the server says. An agent or script that reads these fields must read them there: `name` and `client` (`list_engagements`), `title` (`list_findings`, `list_templates`, `read_template`, `list_notifications`), `markdown` (`read_template`), `text` (`list_notifications`, `read_chat`, `read_finding`'s open threads), `message` and `quote` (`lint_finding`, `get_check_results`, `read_finding`'s violations), `author`, `subject` and `changed` (`list_history`), and in `read_finding` `finding_md`, `assets`, each section's `body` and the `reason` of `state.returned` and `state.withdrawn` (whose `By` is now `by`). A section the configuration does not name has its `name` there too, as has a thread's `section` on it (`read_finding`, `read_chat`), and `field_bases` lists the configured details rows only. IDs, folder names, hashes, bases, statuses and `allowed_actions` did not move. Each such tool's description says it, and `transition`'s asks to confirm each call ([docs/mcp.md](docs/mcp.md)).
- Over MCP, `read_finding` no longer sends `finding_md` (before: the whole file beside the sections, so the text went out twice). The sections have the text, and the front matter comes as fields: `id`, `author`, `severity`, `cvss`, and under `untrusted` `title`, `details`, `cvss_reasons` and `assets`. An agent that parsed `finding_md` reads these fields, or passes `raw: true` to get the file as `untrusted.finding_md`.
- Over MCP, `read_finding` gives at most 20 open threads, the oldest first, each with its last 20 replies. `open_threads_more` and each thread's `replies_more` count what is left out; `read_chat` has all of it.
- Over MCP, a finding file that does not parse answers `<engagement>/<folder>: cannot be read` as its message; the parser's words are `untrusted.detail`.
- Over MCP, `read_finding` gives `attachments_hash`, and `transition` takes it as `attachments_base`: a sign-off, an approval or a completion is then refused with `conflict` when an attachment was added, replaced or removed since. Without it the attachments are not compared.
- The binary embeds the six developer pages only.
- `docs/deploy.md`: a `0700` data folder, systemd hardening, backup pruning, the minimum git version, uninstalling.
- `docs/rules.md` covers every kind of rule, its limits and its failures.
- `docs/known-limits.md` lists today's limits by subject.
- The team of an archived engagement cannot change. Reopen the engagement first.
- Only an admin sets where a service destination publishes (project, issue type, space, parent page).
- Only a director pushes `README.md` to the main repository, as `.gitignore`.
- The vendored htmx is 2.0.11 (before: 2.0.4).
- Submit runs the pattern and built-in rules only, on the finding page, in bulk and over MCP (before: every rule in the request, up to 90 s per finding, and per row in bulk). A script or an AI rule no longer holds a Submit and is not started by one; Check runs them, and Sign off and Approve read that Check as before. On the page, an error a script left in the last Check no longer disables Submit; the count beside it is unchanged. A Submit writes no `gate stayed open` line any more. Approve and Complete with Require Check off still run every rule ([docs/rules.md](docs/rules.md)).
- An AI rule that could not run holds nothing: with Require Check on and a provider set up, a Check whose AI call failed no longer makes Sign off and Approve wait (before: `run check first: an AI check failed; retry it`). Submit was not held before either. The "AI checks failed" badge and Retry stay, what the rule found before on the same text still counts, and a script rule that could not run still fails the Check. Each Sign off, Approve or Complete that goes through this way writes a `warn` line, `checks: an AI rule could not run; the gate stayed open`. An AI rule at level `error` is therefore no guarantee: keep what must hold in pattern, built-in or script rules.
- The pre-commit check (`yars lint --staged`, the hook) runs the pattern and built-in rules only, so a commit no longer waits for scripts and AI calls (before: every rule, up to two minutes). `yars lint --staged --all` asks the server for the scripts and AI rules too; with a Git token it gets them only when the token has the Run checks action, with a password always. An installed hook needs no change. An older `yars` with the new server gets the pattern and built-in rules; a new `yars lint --staged --all` with an older server gets what that server ran before.
- `yars seed` gives its accounts a random password and prints it. Without the size flags it makes 2 engagements of 20 findings with 50 messages (before: 50 of 300, with 10,000).
- `/setup` asks for a setup code. `yars serve` logs the code at each start while there is no account. `yars useradd --admin` needs no code.
- Settings › Tokens › New token asks for your password. `yars token add` does not.
- `ai.api_key_env` and `smtp.password_env` in `.yars/config.yaml` must name a variable that starts with `YARS_`. A file that names another one is refused on save and on push, and `yars serve` does not start with it. Rename the variable in the service's environment, set the new name in `.yars/config.yaml` in the data folder and commit it there ([docs/config.md](docs/config.md)).
- The clone and MCP addresses on the pages come from `base_url`. Without it they use the request's host, and `https` only when the server runs with `--https` or a certificate: the `X-Forwarded-Proto` header is no longer read. A server behind a TLS proxy that runs without `--https` and without `base_url` now shows `http` addresses: set `base_url`. `yars serve` logs at the start when `base_url` is not set.
- A login ends 30 days after it was made at the latest, however much it is used: sessions older than that end at the upgrade. The session cookie lives as long as its session (before: always 14 days, whatever Admin › System › Retention said). Sessions set to 0 days there means the default 14; such sessions are now deleted when they end.
- Only a finding's author or a director sends it to a destination. The export page ticks the findings you may send. Downloads and the preview stay open to the team.
- YARS writes the data folder for the service account alone: folders `0700`, files `0600`, scripts `0700`, and git runs with a umask of `077`. A restore writes these modes too. An existing data folder is not changed: `chmod -R go= <data folder>` closes it.
- The umask of `077` is that of rule scripts, script destinations and pandoc too: a file such a script makes, also outside the data folder, is `0600`. A script whose files another account reads sets its own umask (`umask 022`).
- Standard workflow: an error on your own finding is dismissed, and restored, by another reviewer or a director, whatever your role. Warnings and the simple workflow are unchanged. Dismissals made before stay.
- `yars useradd` and `yars passwd` on a terminal ask for the password twice and do not show it. A password piped to them is a temporary one: the next login asks for a new one, and until then the account's git logins and tokens are refused.
- `yars token add` makes a token that expires after 90 days (before: never). `--days N` or `--expires YYYY-MM-DD` sets another end, `--expires never` or `--days 0` none. A past date is refused. The printed line names the expiry.
- The service log of `yars serve` has a new form: every line is `time=… level=… msg=… key=value …` on stderr (before: free text). A filter on the old text must change. A failed login is now `msg="login failed" user=… remote=…` (git: `msg="git login failed"`), a lockout `msg="login locked"`, the setup code `setup_code=…`. What `git http-backend` and the web server itself report are lines of the same form.
- `yars export`, `yars lint` and `yars mcp` write a finding or an engagement they skip to stderr in the same form.
- A key in `.yars/config.yaml` that YARS does not know stops the start (before: ignored, so `base-url:` read as no address). It is refused on a push and on Admin › Structure too, with the key and its line. `smtp.port` must be 1 to 65535, `smtp.from` an address alone (no name in front) and `smtp.host` a host name alone (no scheme, no port). Check the file before the upgrade; to fix a server that does not start, correct the file in the data folder and commit it there ([docs/config.md](docs/config.md)).
- A destination that makes a file (pandoc, script, Confluence HTML) no longer marks its findings reported unless its file says `mark_reported: true` (before: every destination without the key marked). Jira and a Confluence push still mark without the key. `yars init` writes its two example destinations so; Export › Destinations starts a new destination with Marks reported unticked, ticks it when the destination becomes Jira or a Confluence push, and unticks it when it becomes a file; `yars export --mark` on a destination that does not mark says `not marked: <id> has mark_reported off`. Destination files that say `mark_reported: true`, as the examples of an older `yars init` do, are not changed: set the line to `false` in `.yars/exporters/docx.yaml` and `confluence.yaml` to stop them marking.
- `yars export` writes its file `0600` and does not replace a file that is there. `--force` replaces it. A device or a pipe named by `--out` (`/dev/stdout` into a pipe, a FIFO) is written into as before.
- A webhook's signature covers the time of the request: `X-YARS-Signature` is the HMAC-SHA256 of the new `X-YARS-Timestamp` header (Unix seconds), a dot and the body (before: of the body alone, so a caught request could be sent again at any time). Every receiver must change its check: sign `timestamp + "." + body`, and refuse an old timestamp. A receiver that still checks the body alone refuses every delivery after the upgrade. Each payload has an `id`, also sent as `X-YARS-Event-ID`: it is the same on every try, on a redelivery and for every webhook, so a receiver can drop what it has handled ([docs/webhooks.md](docs/webhooks.md)).
- A webhook delivery is tried 12 times over about three and a half hours (before: 6 times in five minutes): the waits double from 10 s up to one hour. After 5 deliveries given up in a row the webhook is switched off: every admin gets a notification (Webhook off), Admin › Activity has a `webhook.disable` row by `yars`, and the service log a `warn` line, `webhook switched off after failed deliveries`. A delivery that arrives, switching the webhook on and another URL start the count again. A try without an HTTP answer says why in the Deliveries table and in the log's `err`: `timeout`, `DNS`, `connection refused`, `TLS` or `no answer` (before: always `no answer`).

### Fixed

- A server stopped between a commit and the database write that follows it no longer leaves the finding half changed. A director's edit of a complete finding keeps its approval, and a rename in Admin › Structure keeps a finding's approval, sign-offs and chat threads: the next start of `yars serve` makes the write (before: the finding read as in verification). Each such write is in Admin › Activity as `system.repair` by `yars` and one `warn` line of the service log.
- A second `yars serve` on a data folder a server runs on stops at once with `another yars serve runs on this data folder` and changes nothing (before: it reset the work trees, migrated the database and rewrote the push hooks beside the running server). The running server holds a lock on `.yars/yars.db.lock`; the lock ends with its process, the file stays. The account commands and `yars backup` work beside the server as before.
- A push that stops sending, or whose client stops reading the answer, no longer holds its engagement's lock (or the main repository's) and with it every save there. Each push is read whole into a temporary file in `TMPDIR` before git starts, and its answer is sent after the lock is free, so the `remote:` lines arrive when the push has ended. A push or a fetch that sends nothing for two minutes gets `408`, and the service log one `warn` line, `git: a request body stalled and was cut off`; one that keeps sending is never cut. A body announced over 2 GiB is refused before it is read (before: only a chunked one).
- The backup download of Admin › System no longer holds the repositories' locks while the browser takes it (before: a slow or stopped download held the main repository and each engagement in turn, for up to an hour). The ZIP is built as a file in `TMPDIR` first, which needs room for one whole backup, and sent after; the browser gets its size, and a backup that fails is an error page, never a broken download. A download that takes nothing for two minutes is cut; a slow one is not (before: every download ended after an hour).
- `yars userdel` takes the account off the findings it was still to review: drafts and findings in verification it had not signed off (before: the deleted account stayed their reviewer, and a finding waited for it). It prints the count, and the IDs of the findings in verification left without a reviewer or with sign-offs of deleted accounts only; the count is in the `user.delete` row of Admin › Activity. The account's sign-offs, chat, dismissals and check runs stay under its name. The threads it hid are forgotten.
- An attachment change on a finding in verification drops its sign-offs before the commit (before: after it, so a stop in between left sign-offs for files the reviewers never saw). A commit that fails puts them back.
- At each start the database is compared with the finding files once. The row Database and files of Admin › System shows the result until Run integrity replaces it. The row also counts the writes the start made after a stop and the noted writes it could not make, beside an error too.
- The cache of rendered Markdown is limited in bytes; a text over 64 KiB is not cached.
- The editor's preview takes only a finding's folder name in its address.
- Files waiting for download after a send are limited to 256 MiB per user, dropped after 10 minutes by a timer, and served only under the engagement they were made in.
- A reason (Return, Withdraw, Revert, dismissing a check) has at most 4,000 characters, on the finding page and over MCP as in the bulk bar.
- An approval and a sign-off are bound to the full SHA-256 of the finding's file (before: its first 64 bits), and so are the version a Sign off, Approve or Complete button names and the check run they wait for. Approvals, sign-offs and check runs from before the upgrade keep counting. A finding page left open across the upgrade must be loaded again before Sign off or Approve. Over MCP, `read_finding`'s `hash` is the full digest.
- The service log has a line for each failed password login (website and git), with the name and the address, and one for a lockout. A failed AI call logs its status and the provider's host only, no longer the start of the provider's answer.
- A restore takes no git hook from the ZIP and writes each repository's git config again with its basic settings only. A ZIP whose `.git` is a file or holds no `HEAD`, or that holds a git folder (`HEAD`, `objects`, `refs`) outside `.git`, is refused.
- A send to Confluence or Jira and a webhook delivery follow no redirect to another host, another port or from `https` to `http`: the key, the signature and the text go to the configured address only. Such a redirect fails the send with `redirect to <host> refused`.
