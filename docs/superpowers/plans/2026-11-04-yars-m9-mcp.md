# M9 MCP server Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an AI assistant (Claude Code, etc.) read and edit findings through MCP — locally on a clone (`yars mcp`, stdio) or on the server (`/mcp`, HTTP with a per-user token) — with exactly the same permission and workflow rules as the website.

**Architecture:** `internal/mcp` implements the MCP JSON-RPC subset we need (initialize, ping, tools/list, tools/call) by hand — no SDK dependency — and maps tools onto `store`, `index`, `rules` and `workflow` calls made as a `config.User`, so every existing check (CanEdit inside the store lock, Transition rules, gate + lint) applies. Stdio mode works on a local clone (commits locally; the M6 push policy is the final gate); HTTP mode is mounted in `serve` behind Bearer tokens kept in an untracked `.yars/tokens.yaml` (sha256 hashes).

**Tech Stack:** Go 1.27, encoding/json, net/http, bufio.

**Spec:** `docs/superpowers/specs/2026-11-03-yars-design.md` (section "MCP server"): tools list_engagements, list_findings(filter), read_finding, update_section, set_field, add_chat_message, lint_finding, create_finding; same role/transition enforcement.

## Global Constraints
- Protocol: JSON-RPC 2.0; `initialize` returns `{"protocolVersion": <client's if one of 2025-06-18/2025-03-26/2024-11-05 else 2025-06-18>, "capabilities":{"tools":{}}, "serverInfo":{"name":"yars","version":"1"}, "instructions": <short usage text>}`; `notifications/initialized` and other notifications get no response; unknown methods → error -32601; bad params → -32602. Tool errors are returned as results with `isError: true` and a text explanation (not JSON-RPC errors).
- Stdio: one JSON message per line on stdin/stdout; logs to stderr only.
- HTTP: `POST /mcp` with `Authorization: Bearer <token>`, JSON body, JSON response (`Content-Type: application/json`); notifications → 202 empty; `GET /mcp` → 405; missing/invalid token → 401. Mounted outside the cookie session (no CSRF exposure: no cookies are accepted on this route).
- Tokens: `yars token add <user>` prints a new random token once (32 bytes, hex, prefixed `yars_`) and stores `{user, sha256, created}` in `.yars/tokens.yaml` (0600, git-ignored like users.yaml); `yars token list`, `yars token revoke <user>`. Tokens are loaded at serve start (like users).
- Tools (all args are strings unless noted; `engagement` = engagement ID, `finding` = finding dir or ID like `F-001`):
  - `list_engagements {}` → id, name, client, type, source.
  - `list_findings {engagement, status?, severity?}` → id, dir, title, status, severity, score, author, reviewers, open_threads, retest_result.
  - `read_finding {engagement, finding}` → the raw finding.md, plus JSON meta, section names, per-section base hashes, CVSS/details hashes, open chat threads (text) and fast-rule violations.
  - `create_finding {engagement, title}` → id + dir.
  - `update_section {engagement, finding, section, body, base?}`.
  - `set_field {engagement, finding, field, value}` — fields: `title`, `severity`, `cvss` (vector or ""), `cvss_reason.<METRIC>`, `details.<Row>`, `reviewers` (comma-separated), `retest_result`.
  - `transition {engagement, finding, action, reason?}` — submit/return/clear/approve/reopen (report only via exporters).
  - `add_chat_message {engagement, finding, text, section?, reply?}`; `resolve_thread {engagement, finding, thread}`.
  - `lint_finding {engagement, finding, all? (bool)}` — fast rules by default; `all` also runs scripts/AI.
- Every write goes through the store as the authenticated `config.User` (stdio: `--user` and `--role`, default role pentester; the push policy re-checks on push). New store method `UpdateTitle(engID, dir, title string, a Actor)` (content edit; non-empty, single line, max 200 chars; commit `F-001: edit title`).
- Finding lookup by ID (`F-001`) resolves to the dir with that ID prefix in the engagement.
- Shell usage: Write/Edit for files; single plain commands.

## Review Focus
1. A pentester using MCP tries to approve, edit a complete finding, or set someone else's clearance: refused exactly as on the web (Task 1 `TestMCPPermissions`).
2. Malformed JSON, unknown method, missing args, a huge body: proper JSON-RPC errors, server keeps running (Task 1 `TestMCPProtocolErrors`, HTTP body cap 2 MB).
3. `finding` args with path tricks (`../`, `F-001/../../x`): not found (Task 1 `TestMCPLookup`).
4. HTTP token: wrong/missing/revoked token → 401; tokens never logged; token file never committed (Task 2 `TestMCPHTTPAuth`, `TestTokensUntracked`).
5. Stdio mode on a clone: writes commit locally as the user and a later push of those commits passes the M6 policy for a legitimate edit (Task 2 `TestMCPStdioThenPush`).
