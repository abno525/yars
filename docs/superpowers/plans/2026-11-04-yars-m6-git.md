# M6 Git smart HTTP + pre-receive enforcement Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Team members clone the data repo from the YARS server, edit findings locally (by hand or with AI), and push back; a pre-receive check enforces the same workflow, permission and rule constraints as the web UI.

**Architecture:** `internal/gitserve` wraps `git http-backend` (net/http/cgi) behind HTTP Basic auth with YARS accounts and installs a `pre-receive` hook that runs `yars hook pre-receive`. `internal/policy` compares old and new trees of a push (via the git CLI) and decides, per changed file, whether the pushing user may make that change, reusing `workflow` and `rules`. The server's checked-out working tree is updated in place (`receive.denyCurrentBranch=updateInstead`), so the index and the web UI see pushed changes immediately.

**Tech Stack:** Go 1.27, net/http/cgi, git CLI (`http-backend`, `receive-pack`, `diff`, `show`), bcrypt.

**Spec:** `docs/superpowers/specs/2026-11-03-yars-design.md` (section "Git model").

## Global Constraints
- Clone URL: `http(s)://<host>/git/yars` (fixed repo name `yars`); maps to the data repo directory.
- Auth: HTTP Basic with YARS username + password; every git request requires auth (fetch and push). Successful credentials are cached in memory for 10 minutes keyed by sha256(user + ":" + password) to avoid bcrypt per request. `REMOTE_USER` is set for http-backend so hooks know the pusher.
- Server repo config set at `serve` start: `http.receivepack=true`, `receive.denyCurrentBranch=updateInstead`, `receive.denyNonFastForwards=true`, `receive.denyDeletes=true`. The hook file `.git/hooks/pre-receive` is (re)written at start: `#!/bin/sh` + `exec '<abs path of yars binary>' hook pre-receive --data '<data dir>'`.
- Only the checked-out branch (`refs/heads/master` or whatever HEAD points to) may be updated; any other ref is rejected.
- Policy (evaluated against the server's current config, users and rules — a push can't relax its own checks):
  - Changes to `.yars/**` (config, users, rules, scripts) only by role `admin` or `director`.
  - Allowed paths: `.yars/**`, `.gitattributes`, `engagements/<eng>/engagement.yaml`, `engagements/<eng>/findings/<dir>/finding.md`, `.../chat.jsonl`, `.../attachments/**`, `engagements/.gitkeep`, `README.md`. Anything else → rejected ("findings must live under an engagement").
  - `engagement.yaml` add/modify/delete only by admin/director (same as the web).
  - New `finding.md`: must parse, status `draft`, `id` matches the directory prefix (`F-007-…` ↔ `id: F-007`), no duplicate ID within the engagement.
  - Modified `finding.md` (old → new metas): must parse; if old status is complete/reported, `workflow.CanEdit(pusher, old)` must hold for any change. Status change must match exactly one action's (from, to) with `workflow.Check(pusher, old, action)`; for submit/approve also `workflow.Gate(new)` and no error-level rule violations (all rule kinds) on the new version. `cleared_by` may only gain the pusher (and only via a legitimate clear: status verification, pusher assigned reviewer, not author) and may lose anyone. `returned` may only be set by a legitimate return. `author` and `id` may not change.
  - Deleted `finding.md`: only admin/director.
  - `chat.jsonl`: new content must start with the old content byte-for-byte (append-only); every appended message must have `user` = pusher and no `event` field (events come only from transitions; a pushed status change gets no event line — ruling).
  - Each section body must pass `finding.ValidateBody`.
- Rejection output: one line per problem, `yars: <path>: <reason>`, printed to stderr of the hook (git shows it as `remote: …`), exit 1.
- Web writes and pushes share the repo: a concurrent web commit during a push may fail with git's index lock; the web write is then rolled back and reported as an error (ruling, acceptable at team scale).
- UI: the engagements page shows the clone command `git clone http://<host>/git/yars` with a one-line hint.

## Review Focus
1. Push that edits `.yars/users.yaml` as a pentester (e.g. to add an admin): rejected (Task 2 `TestPolicyYarsDir`).
2. Push that sets `cleared_by: [bob]` as alice, or flips status draft → complete directly: rejected with a clear reason (Task 2 `TestPolicyStatusAndClearance`).
3. Push that rewrites history (`--force`) or deletes the branch: rejected by receive config (Task 3 `TestPushForceRejected`).
4. Fetch/push without or with wrong credentials: 401, never served (Task 1 `TestAuthRequired`).
5. A pushed edit is visible in the web UI immediately (working tree updated) and a rejected push leaves the server repo untouched (Task 3 `TestPushEndToEnd`).

### Task 1: `internal/gitserve` — authenticated git http-backend

**Files:** Create `internal/gitserve/gitserve.go`, `internal/gitserve/gitserve_test.go`; Modify `internal/auth/auth.go` (`func (a *Auth) Check(username, password string) (config.User, bool)` — bcrypt check without creating a session, constant-time for unknown users as in Login).

**Interfaces — Produces:**
- `type Server struct{ Repo *gitrepo.Repo; Auth *auth.Auth; HookCmd string }`.
- `func (s *Server) Setup() error` — writes git config keys and the pre-receive hook (if `HookCmd` non-empty).
- `func (s *Server) Handler() http.Handler` — mounted at `/git/`; strips `/git/yars`, runs `git http-backend` with `GIT_PROJECT_ROOT=<data dir>`, `PATH_INFO=<rest>`, `GIT_HTTP_EXPORT_ALL=1`, `REMOTE_USER=<user>`; 401 with `WWW-Authenticate: Basic realm="yars"` when auth fails; 404 for other repo names.
- Web: `Server.Git http.Handler` mounted on the root mux at `/git/` (outside session auth and outside CrossOriginProtection's cookie concern — git requests carry no cookies; mount it before the CSRF wrapper).

### Task 2: `internal/policy` — push rules

**Files:** Create `internal/policy/policy.go`, `internal/policy/policy_test.go`.

**Interfaces — Produces:**
- `type Update struct{ Old, New, Ref string }`.
- `type Checker struct{ Repo *gitrepo.Repo; Cfg config.Config; Users []config.User; Linter store.Linter }`.
- `func (c *Checker) Check(user string, ups []Update) []string` — problems (empty = accept). Uses `git diff --name-status -z <old> <new>` and `git show <rev>:<path>`; `Old` all-zero = new branch (rejected unless it's the checked-out branch and the repo is empty).
- gitrepo helpers: `func (r *Repo) ChangedFiles(old, new string) ([]Change, error)` with `Change{Status byte; Path string}` and `func (r *Repo) Show(rev, path string) ([]byte, error)`; `func (r *Repo) CurrentBranch() (string, error)`.
