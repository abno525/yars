# Changelog

What changed for people who run or use YARS. Newest first.

## Unreleased

### Added

- Settings › About shows the version, the license and a link to the source.
- The licence texts of the vendored fonts and htmx ship with the binary; `NOTICE` lists all third-party work.
- `SECURITY.md`, `CONTRIBUTING.md` and issue templates.
- `log.level` (`debug`, `info`, `warn`, `error`) and `log.format` (`text`, `json`) in `.yars/config.yaml`, and `yars serve --log-level`, set what the service log holds and how it is written ([docs/config.md](docs/config.md)). Both keys are read at the start.
- The service log has one line for each request to the website, the git endpoint and MCP: an ID, the method, the route, the status, the time taken, the account, the token's ID, the engagement and the finding. A request over 2 s is a warning. Static files are logged at `debug`. A handler's panic is one line with the whole stack trace in `stack`.
- The service log holds IDs and usernames, never text: an attribute named like a password, a token's value, a key, a cookie, a title, a reason or other text is dropped, and an error's text loses a finding's folder name (its ID stays), an attachment's name, and the login and query of an address. The error of a failed git command leaves out the commit message.
- Every response carries its request's ID as `X-Request-ID`. An internal error shows it on the page and in the toast (`Request 4f2a9c1b`), and the error's log line has the same ID.
- The background work writes a line when it ends, with the time taken and the outcome: a check run, an AI call, an export, a webhook delivery, a mail, a push (accepted or refused), a backup download, a restore upload and the daily prune. A webhook delivery that is tried again, a failed AI call, a mail that is not sent and a wait of over 5 seconds for a repository's lock are warnings. The start line names the version, the schema, the workflow, the address and whether AI, SMTP and pandoc are on.
- An AI call the provider refused is one `warn` line, `ai call failed`, with `status` and `host`. The line `ai: the provider refused a call` is gone.
- A webhook delivery that got no HTTP answer says why in `err`, in one fixed word (`no answer`, `redirect refused`, `secret`, `address`, `removed`, `disabled`, `database`). A delivery dropped because its webhook was turned off is an `info` line, `webhook delivery dropped`.
- `yars status --data <dir>` prints what the running server does now: the checks running and queued, the waiting webhook deliveries, the open event streams, the repository locks and the last 200 warnings and errors. It reads the server over a socket in the data folder (`.yars/status.sock`), needs no password, and runs as the service account. A second `yars serve` on the same data folder leaves the first one's socket alone: it writes one `warn` line and runs without `yars status`.
- Admin › System has two new panels. Current state shows the same as `yars status`. Log shows the last 200 warnings and errors of the service log; they are kept in memory and lost at a restart.
- Admin › System › Log has the switch Debug level for 15 minutes: it sets the service log to `debug` without a restart and turns itself off. Each change is in Admin › Activity.
- `docs/deploy.md` has a Logs section: the journalctl commands, the levels, the fields, what a line never holds, the request ID, and a fail2ban example for the failed-login lines in their new form.

### Changed

- The Go module is `github.com/abno525/yars`: `go install github.com/abno525/yars/cmd/yars@latest` builds the binary.
- The binary embeds the six developer pages only.
- `docs/deploy.md`: a `0700` data folder, systemd hardening, backup pruning, the minimum git version, uninstalling.
- `docs/rules.md` covers every kind of rule, its limits and its failures.
- `docs/known-limits.md` lists today's limits by subject.
- The team of an archived engagement cannot change. Reopen the engagement first.
- Only an admin sets where a service destination publishes (project, issue type, space, parent page).
- Only a director pushes `README.md` to the main repository, as `.gitignore`.
- The vendored htmx is 2.0.11 (before: 2.0.4).
- An AI rule that could not run holds nothing: with Require Check on and a provider set up, a Check whose AI call failed no longer makes Sign off and Approve wait (before: `run check first: an AI check failed; retry it`). Submit was not held before either. The "AI checks failed" badge and Retry stay, what the rule found before on the same text still counts, and a script rule that could not run still fails the Check. Each Submit, Sign off, Approve or Complete that goes through this way writes a `warn` line, `checks: an AI rule could not run; the gate stayed open`. An AI rule at level `error` is therefore no guarantee: keep what must hold in pattern, built-in or script rules.
- The pre-commit check (`yars lint --staged`, the hook) runs the pattern and built-in rules only, so a commit no longer waits for scripts and AI calls (before: every rule, up to two minutes). `yars lint --staged --all` asks the server for the scripts and AI rules too; with a Git token it gets them only when the token has the Run checks action, with a password always. An installed hook needs no change. An older `yars` with the new server gets the pattern and built-in rules; a new `yars lint --staged --all` with an older server gets what that server ran before.
- `yars seed` gives its accounts a random password and prints it. Without the size flags it makes 2 engagements of 20 findings with 50 messages (before: 50 of 300, with 10,000).
- `/setup` asks for a setup code. `yars serve` logs the code at each start while there is no account. `yars useradd --admin` needs no code.
- Settings › Tokens › New token asks for your password. `yars token add` does not.
- `ai.api_key_env` and `smtp.password_env` in `.yars/config.yaml` must name a variable that starts with `YARS_`. A file that names another one is refused on save and on push, and `yars serve` does not start with it. Rename the variable in the service's environment, set the new name in `.yars/config.yaml` in the data folder and commit it there ([docs/config.md](docs/config.md)).
- The clone and MCP addresses on the pages come from `base_url`. Without it they use the request's host, and `https` only when the server runs with `--https` or a certificate: the `X-Forwarded-Proto` header is no longer read. A server behind a TLS proxy that runs without `--https` and without `base_url` now shows `http` addresses: set `base_url`. `yars serve` logs at the start when `base_url` is not set.
- A login ends 30 days after it was made at the latest, however much it is used: sessions older than that end at the upgrade. The session cookie lives as long as its session (before: always 14 days, whatever Admin › System › Retention said). Sessions set to 0 days there means the default 14; such sessions are now deleted when they end.
- Only a finding's author or a director sends it to a destination. The export page ticks the findings you may send. Downloads and the preview stay open to the team.
- YARS writes the data folder for the service account alone: folders `0700`, files `0600`, scripts `0700`, and git runs with a umask of `077`. A restore writes these modes too. An existing data folder is not changed: `chmod -R go= <data folder>` closes it.
- The umask of `077` is that of rule scripts, script destinations and pandoc too: a file such a script makes, also outside the data folder, is `0600`. A script whose files another account reads sets its own umask (`umask 022`).
- Standard workflow: an error on your own finding is dismissed, and restored, by another reviewer or a director, whatever your role. Warnings and the simple workflow are unchanged. Dismissals made before stay.
- `yars useradd` and `yars passwd` on a terminal ask for the password twice and do not show it. A password piped to them is a temporary one: the next login asks for a new one, and until then the account's git logins and tokens are refused.
- `yars token add` makes a token that expires after 90 days (before: never). `--days N` or `--expires YYYY-MM-DD` sets another end, `--expires never` or `--days 0` none. A past date is refused. The printed line names the expiry.
- The service log of `yars serve` has a new form: every line is `time=… level=… msg=… key=value …` on stderr (before: free text). A filter on the old text must change. A failed login is now `msg="login failed" user=… remote=…` (git: `msg="git login failed"`), a lockout `msg="login locked"`, the setup code `setup_code=…`. What `git http-backend` and the web server itself report are lines of the same form.
- `yars export`, `yars lint` and `yars mcp` write a finding or an engagement they skip to stderr in the same form.
- A key in `.yars/config.yaml` that YARS does not know stops the start (before: ignored, so `base-url:` read as no address). It is refused on a push and on Admin › Structure too, with the key and its line. `smtp.port` must be 1 to 65535, `smtp.from` an address alone (no name in front) and `smtp.host` a host name alone (no scheme, no port). Check the file before the upgrade; to fix a server that does not start, correct the file in the data folder and commit it there ([docs/config.md](docs/config.md)).
- A destination that makes a file (pandoc, script, Confluence HTML) no longer marks its findings reported unless its file says `mark_reported: true` (before: every destination without the key marked). Jira and a Confluence push still mark without the key. `yars init` writes its two example destinations so; Export › Destinations starts a new destination with Marks reported unticked, ticks it when the destination becomes Jira or a Confluence push, and unticks it when it becomes a file; `yars export --mark` on a destination that does not mark says `not marked: <id> has mark_reported off`. Destination files that say `mark_reported: true`, as the examples of an older `yars init` do, are not changed: set the line to `false` in `.yars/exporters/docx.yaml` and `confluence.yaml` to stop them marking.
- `yars export` writes its file `0600` and does not replace a file that is there. `--force` replaces it. A device or a pipe named by `--out` (`/dev/stdout` into a pipe, a FIFO) is written into as before.

### Fixed

- The cache of rendered Markdown is limited in bytes; a text over 64 KiB is not cached.
- The editor's preview takes only a finding's folder name in its address.
- Files waiting for download after a send are limited to 256 MiB per user, dropped after 10 minutes by a timer, and served only under the engagement they were made in.
- A reason (Return, Withdraw, Revert, dismissing a check) has at most 4,000 characters, on the finding page and over MCP as in the bulk bar.
- An approval and a sign-off are bound to the full SHA-256 of the finding's file (before: its first 64 bits), and so are the version a Sign off, Approve or Complete button names and the check run they wait for. Approvals, sign-offs and check runs from before the upgrade keep counting. A finding page left open across the upgrade must be loaded again before Sign off or Approve. Over MCP, `read_finding`'s `hash` is the full digest.
- The service log has a line for each failed password login (website and git), with the name and the address, and one for a lockout. A failed AI call logs its status and the provider's host only, no longer the start of the provider's answer.
- A restore takes no git hook from the ZIP and writes each repository's git config again with its basic settings only. A ZIP whose `.git` is a file or holds no `HEAD`, or that holds a git folder (`HEAD`, `objects`, `refs`) outside `.git`, is refused.
- A send to Confluence or Jira and a webhook delivery follow no redirect to another host, another port or from `https` to `http`: the key, the signature and the text go to the configured address only. Such a redirect fails the send with `redirect to <host> refused`.
- Admin › Rules › Test bench runs with a POST: a link cannot start scripts or AI calls. A long Run on engagement is no longer cut off after 60 seconds.
- Over MCP a failure of the server itself answers `server_error` with the message `internal error`, and `read_finding` gives that as an action's reason. The error's own words (a path, a database statement) go to the service log only. A finding file that does not parse still says why.
- The browser keeps no page snapshots (htmx's history cache is off; Back to such a page loads it again). A draft kept after an expired session is stored under its account's name, so another account on the same browser is not offered it, and Log out removes the account's drafts. A draft is kept 14 days: an older one, of any account, is removed when a page loads. Drafts kept by an earlier version are removed.
- Dismissing a check result and restoring it are in the audit log: who, the finding, the rule, its level and place, and the reason. A dismissal without a reason is refused by the server itself, not only by the page.
- Fix with AI sends the section between the same delimiters as an AI check, so text in a finding cannot pass as the rule.
- A new account cannot take a username that differs from another only in the case of its ASCII letters (`Alice` beside `alice`). Accounts that already do keep working; `yars serve` logs them at start. The database schema is 25.
- Live updates of an open page end within 25 seconds of a logout, a disabled account or leaving the team. One account holds at most 20 live streams.
- A merge into a complete or reported finding keeps its approval also when the source brings a new asset (before: the finding fell back to verification). The `finding.updated` webhook of a metadata edit names the reviewers.
- The Merge page has the panel Not moved: the source's details rows and CVSS, which the target does not take.
- A push of a finding or a template with text between the front matter and the first `## ` heading is refused: no page shows such text and no export carries it. A file that already has it still takes other edits.
- A push of a finding or a template whose front matter the website cannot edit is refused: the whole of it between `{ }`, an indented top-level key, a value continued at the first column ([docs/git.md](docs/git.md)). Before, every later edit of its title, severity, CVSS, details or assets failed, and it stopped a rename in Admin › Structure. A file the server already holds in such a form is not changed: it still stops the rename until it is rewritten.
- Saving the reviewers of a finding from a page opened before someone else changed them is refused (`the reviewers changed since you opened the page; choose again`): the reviewer added meanwhile, and their sign-off, stay. Assign all adds to the list as it is. Over MCP, `read_finding` gives `field_bases.reviewers`, and `set_field reviewers` with it as `base` answers `conflict` when the list changed.
- Each start of `yars serve` removes the files in the engagements' `findings/` folders that no commit holds, and logs the engagement and a count (`warn`). A stop between a file's write and its commit left a new finding's folder or a new attachment that every page read as real. Nothing is removed while another `yars serve` answers on the data folder, nor in the main repository. A file an operator put into a `findings/` folder by hand, without a commit, is removed too.
- An engagement repository a stop left without its first commit no longer stops the start.
- A service account whose git config sets `init.defaultRefFormat=reftable` works: YARS makes its repositories with refs as files, and reads the commit of a repository that is reftable already by asking git.
- A retest copies complete and reported findings only: New retest lists those, and a draft, a finding in verification or a withdrawn one is refused by name. The retest's dates and client are checked as on its Settings tab, and the retester must be an account that is not disabled. A finding named by its number is copied into a folder of its own name, once.
- A CVSS reason goes with the value it explains. Saving a vector with a changed metric removes that metric's reason unless a reason for the new value is saved with it, and clearing the vector removes every reason (before: the old reason stayed, passed the check for the new value and was exported beside it). The CVSS editor empties the reason field of a changed metric and counts it as missing; back at the saved value the reason shows again. Over MCP, `set_field cvss` does the same.
- Admin › Structure renames a name in findings, templates and report text only when its own row was retyped. Removing one name and adding another in the same save is a removal and an addition (before: read as a rename, which rewrote every finding): a removed name that is still used is refused.
- Saving an engagement's Settings rewrites only the lines of the values that changed in `engagement.yaml` (before: the whole file, so pushed comments and other keys vanished). An emptied date removes its key. A file written between `{ }` or with an indented key is refused on the page; change it with git.
- A finding file is written with CRLF line endings only when its front matter uses them on every line (before: one CRLF line anywhere, a pasted HTTP response say, turned every line of the file to CRLF at the next edit). A CRLF line in an LF file is written back with LF.
- History lists every commit as it is: a pushed commit whose author name or subject holds a control character is no longer left out or shown as two entries, and a file name with a quote or a space at its end is read as it is.
- The board's and the Report tab's severity counts follow a change of the severities at once (before: the old names and order stayed until a finding of the engagement changed).
- Findings are ordered by their number in every list and in exports: F-999 comes before F-1000, and a pushed F-7 before F-012 (before: as text). A folder outside the F-number scheme comes last.
- A `CVSS:3.0` vector is still taken and stored as the `CVSS:3.1` vector of the same metrics, and now this is said: in the message of MCP's `set_field cvss`, and in the CVSS editor after such a vector is pasted, also when Save takes the paste without Apply, and on a template's page after its CVSS field was saved with one (before: rewritten without a word). The score is the same. A push still refuses a 3.0 vector and names the 3.1 form.
- An uploaded BMP or WebP picture is stored as a PNG under a `.png` name, and so is a redacted copy (before: a BMP showed as `[image removed]` in every export, a WebP was missing from the PDF). The file's bytes decide, not its name. A picture that cannot be read, an animated WebP, or one over 16 megapixels is refused; one picture is converted at a time. A BMP or WebP that a push or an earlier version stored is converted when it is exported. New module: `golang.org/x/image`.
- Every export (PDF, Word, HTML, Confluence, Jira, the preview) has a finding's sections in the configured order, then the sections the configuration does not name (before: in the order of the file, which a push may write in any order). A script destination reads each finding's `sections` list in that order too.
- A Confluence push never takes a page by its title. With no page remembered for the destination, a new page is made (before: the first page of that title in the space was overwritten and its pictures removed, also a page of another engagement of the same name or one a person wrote). Confluence refuses a second page of one title; the refusal now says why a new page was being made. `yars export` remembers its pages as the website does, in the same rows, so a second run updates the page of the first; a push of several findings has a page of its own. A first push that fails after its page was made (a picture's upload, the page's text) remembers that page, and the next push fills it.
- The report's summary is the first report section, whatever it is called (before: only a section named exactly "Executive summary"; under another name the summary was empty and the text stood under Scope and overview). With "Executive summary" not first in Admin › Structure, the first section is now the summary and "Executive summary" is a section under Scope and overview.
- Every git command the server runs has the 2-minute limit: reading a batch of files or sizes and making a repository had none, so a git that hung held its request and the repository's lock without end. It now fails with `timed out after 2m0s`.
- A finding whose author stored a personal key for Jira or Confluence is not sent when that key cannot be read (before: it went out with the server's key, under the server account's name, without a word). The finding fails with `<author>: personal key unreadable`, nothing reaches the service, and the result offers Renew key and Use server key as for any failed key.
- A rule that finds more than the 20 results it shows says so: a last row `and 5 more` (`and more than 1000 more` past 1,000), for pattern, built-in, script and AI rules, counted over the whole finding (before: the rest was dropped without a word, and a pattern rule stopped at 20 per part). The row has the rule's level, counts as one result, is dismissed for its count and opens no chat thread. A rule's line in the Checks strip counts the hidden results too. Over MCP and in `yars lint` the row's target is `more:<n>`. Stored script and AI results are made again at the next check.
- The name of a deleted account (`yars userdel`) stays taken: `yars useradd`, Admin › Users and `/setup` refuse it, also in another case of its letters, with `user bob was deleted: the name stays taken` (before: a new account of that name got the old one's sign-offs, chat, dismissals and findings). There is no way to free a name. Names deleted before the upgrade are not known.
- A finding's text reaches Jira as text: `{` and `}` outside a code block are escaped, in the sections, the summary table, the CVSS explanations and a section's name (before: `{color}`, `{panel}` or `{html}` in a finding was a macro in the issue). A code block names its language only when Jira knows it (`js` becomes `javascript`; `http` and any other word give a block without a language, where Jira showed an error), a code block that holds `{code}` is sent as `{noformat}` so it cannot end itself, and a line of the other fence character no longer ends a block.
- A Markdown table in a finding is a table in the Jira issue (before: its lines were sent as they were, with the line of dashes as a row). An empty cell of the summary and CVSS tables no longer reads as a header cell.
- A Jira destination's file can name the priority of each severity: `priorities` under `jira:` ([docs/exporters.md](docs/exporters.md)). An empty name sends no priority. Without the key the names are Jira's defaults, as before. Export › Destinations keeps the key on save.
- An AI rule's reply without the `violations` list (`{}`, an error object, `null`) is a failed check, `AI check failed: reply has no violations list`, and is not kept (before: read as a pass and kept). Admin › AI › Test fails on such a reply too. A pass kept from such a reply before the upgrade stays until its text changes.
- An AI rule's result quotes the checked text or is dropped: a violation whose quote is not in the part that was sent (a paraphrase, a made-up sentence) is no row, and the service log counts the dropped ones (`ai: violations whose words are not in the text are dropped`). A quote that differs from the text only in its spaces and line breaks becomes the text's own words. Results kept before the upgrade are checked the same way when they are shown; nothing is sent again.
- A call to the AI provider that is answered with status 429, 500, 502, 503, 504 or 529 is made again, twice at most, after 1 s and 2 s or the wait the provider's `Retry-After` names (up to 10 s), within the question's 60 s (before: one answer of that kind failed the check). Rule checks, Fix with AI and Admin › AI › Test all do. In one check only the first question that fails so is tried again: the questions after it are asked once, so a provider that is down does not use up the check's 90 s. Each try that is made again is a `warn` line, `ai call failed; it is tried again`.
- Over MCP on the server, `lint_finding` with `all: true` is a stored check run, as `start_check` starts (before: it ran scripts and AI calls inside the call, past the limit of `checks.max_running`, and on archived engagements too). It waits in the queue, posts each new violation as a chat comment, notifies as a check does, and is refused on an archived engagement. The answer waits for the run, 90 s at most, and has the same `items` plus `run_id` and `state`; when the run is still queued or running, `items` is empty and `message` says to read `get_check_results`. The plain `lint_finding` and `yars mcp` on a clone are unchanged.
- The rule editor (Admin › Rules) has two more boxes for a pattern: Multiline (`(?m)`: `^` and `$` match at each line) and Check empty parts (`require_nonempty`, for a pattern the text must match). Flags written by hand, `(?i)`, `(?m)`, `(?im)` in any order, show as ticked boxes; another flag group, as `(?s)`, stays in the pattern as typed. Before, neither could be set on the page. Pressing Save on a rule with nothing changed is no commit (before: an internal error).
- `yars` builds for Windows (`GOOS=windows go build ./cmd/yars`), for the pre-commit check there (`yars lint --staged`, `yars hook install`). On a system that is not Unix a rule script's timeout stops the script but not the processes it started, and Admin › System shows the disk as unknown.
- `yars lint` on the data folder leaves out the results dismissed on the finding page: a dismissed error is not printed and no longer makes the exit code 1. `yars lint --all` there uses the AI settings saved on Admin › AI (before: `config.yaml` only, so Off on the page still sent text). A clone has no database and is checked as before.
- `yars lint --staged` without `--warn-only` exits 3 when the server could not be asked (down, slow, login refused, no saved login, not an engagement clone); before it exited 0, as for a clean check. With `--warn-only`, as the pre-commit hook runs it, the code is 0 as before: the hook never blocks a commit.
- A rule given another ID on Admin › Rules keeps its dismissals: they move to the new ID in every engagement, and Admin › Activity has a `rules.rename` row with both IDs and the count (before: every dismissed result of the rule counted again). The results of the stored check runs move too, so a dismissed result stays dismissed before the next Check, in archived engagements as well, and the next Check keeps each result's chat thread. A rule renamed by hand in its file is still a new rule.
- Deleting a script rule on Admin › Rules removes its script in the same commit, and so does saving the rule with a script of another name or as another kind (before: the file stayed in `.yars/rules`). A script another rule names stays, and so does a file no rule names.
- An OpenAI-compatible model that answers 400 to `temperature` or `response_format` is asked once more without both, and without them from then on until a restart (before: every check of such a model failed with `HTTP 400`). An OpenAI answer cut at the model's limit (`finish_reason: length`) or withheld by the provider's filter is a failed check, `AI check failed: the reply was cut off`, and is not kept.
- A call to the AI provider follows no redirect to another host, another port or from `https` to `http`: the key and the finding's text go to the configured address only.
- The daily prune deletes finished webhook deliveries and notifications older than the Check runs days of Admin › System › Retention (before: both tables only grew, and a delivery keeps its whole payload). A webhook's newest delivery and a delivery still waiting stay, and an unread notification is kept for at least 90 days; 0 days keeps all. The prune's line in Admin › Activity and in the service log counts them. The audit log has an index on its time. The database file does not shrink. The database schema is 27.
- A draft kept after an expired session remembers the version of the section it was written over. Restore and Save in an editor opened later show the conflict view when someone else saved the section meanwhile (before: the restored text replaced theirs without a word). A draft kept by an earlier version always shows the conflict view. A draft now stays until its text is saved or cancelled; a conflict no longer removes it.
- The CVSS editor asks before unsaved changes are lost: Cancel, Esc, a link and closing the tab ask "Discard changes?" once a metric or a reason differs from what the editor opened with (before: nothing asked).
- "is editing" stays while the editor's tab is in the background (before: it went after 60 s). An editor whose tab was closed is shown for up to 150 s (before: 60 s).
- Keyboard shortcuts work on a layout without Latin letters (Russian, Greek): a letter key counts as the Latin letter of its place, so Ctrl+S saves and Ctrl+K opens Go to (before: nothing happened and Ctrl+S opened the browser's Save). The same holds for a Latin layout's letter outside ASCII on a letter key (Turkish, Azeri); other Latin keys are unchanged.
- Go to: Enter opens a finding only from the list for the text in the field (before: Enter pressed right after typing opened a row of the earlier text). Until that list is there, Enter does nothing. The Enter that ends an input method's composition opens nothing.
- The findings list keeps its filter, sort and search when you come back to it: the crumb of a finding and of its pages, Findings in the top bar (and `f`), the Findings tab and Cancel on New finding and New retest lead to the list as you left it (before: the whole list, unsorted). Kept per browser tab, account and engagement, until the tab closes or you log out. On the list itself, Findings shows the whole list.
- A page whose live updates fell back to the 30 s poll (a server restart, too many open streams, an expired session) goes back to live updates by itself, within 30 s of the stream working again (before: it polled until it was reloaded). "Session expired" is shown once per expiry for the page's own polling (before: again at every poll), and again for a request you send while it is not showing. After a server restart a page that reconnects always loads its parts again (before: it could skip the first changes of the new server).
- An editor's preview is one request at a time: a preview still under way is dropped when the next is sent, so an older answer never shows over a newer text. The editor of a text over 64 KiB waits 1 s after a pause before it asks (300 ms otherwise).
- History › Restore asks first ("Restore Impact?"); before, one click replaced the section's text.
- Shift+L hides or shows the chat on the finding page (before: Ctrl+H, which kept the browser's History from opening there and was taken from the chat box too). Ctrl+H is the browser's own again.
- A double click on a button sends its form once: New finding's Create made two findings, a switch on Admin › Users flipped back, Add user lost the temporary password. The buttons of a sent form are grey for 3 seconds. A double click on Send or Reply in the chat posts one message.
- Copy works on a plain `http` address that is not `localhost` (before: the button did nothing there). When the browser refuses, the toast says "Copy failed" and the text is selected.
- A screen reader hears a reviewer's sign-off on the finding page ("bob (signed off)"; before: the chip's colour alone said it), and Go to's rows are options of its list, the selected one marked.
- Opening a finding marks your notifications of that finding read, and the Inbox number on that page already counts without them (before: only Open on a notification and Mark all read did, so read notices piled up). A part of the page that refreshes itself and a browser's prefetch mark nothing; reading a finding over MCP marks nothing.
- A notification about a chat message opens the finding at that thread, from the notifications page, the inbox and the mail's link (before: at the top of the page). Notifications stored before the upgrade lead to the top. The database schema is 28; the upgrade keeps a copy of the database as `yars.db.before-v27`.
- The notifications page lists 50 rows and loads 50 more at a time (before: the newest 200 and no way to the older ones).
- The title of a new finding takes 200 characters and a Return, Withdraw or Revert reason 4,000, as the server allows.
